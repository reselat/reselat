## 2.1 部署方向确认补记（2026-10-31）

用户在确认30企业服务目标后，明确要求“自己的服务器单独部署”。按最近一轮澄清记录为：**每家企业可在其自己的服务器独立部署ERP**，作为二期交付基线；后续如用户补充不同范围，以最新指令为准。

这更新了本文第7节“部署路线尚未定案”的候选状态：企业私有部署已成为已选方向；共享多租户单实例不再作为本轮默认交付路线。仍保留一套可维护的产品代码，具体版本发行与升级方式待设计。

需要继续确认的边界：你和运营团队如何获得各企业授权、是否建设集中辅导管理入口、哪些汇总数据允许集中、连接中断时如何处理、AI资料外发和Bot运行位置。不能由“统一带运营30家”推导出企业已授权集中复制客户资料、聊天或数据库。

助手当前建议（尚未作为用户已批准设计）：每个企业实例分别保存身份、业务、附件、知识和Bot会话；集中入口管理企业服务、版本和通用课程，跨企业业务操作经独立授权、权限校验和审计。私有部署本身不替代权限、备份、恢复或AI外发控制。

## 2.2 临时授权确认补记（2026-10-31）

用户明确选择：**你和运营团队访问企业独立部署的ERP时采用临时授权**，不是默认长期业务访问。

已经确认的是访问方式；以下为待审设计建议，未视为用户已逐项批准：

- 企业指定审批人授予指定操作人员访问，可限定企业、业务模块、客户／订单和操作类型。
- 每次授权有开始与到期时间，到期自动失效，企业可提前撤销；续期需要重新授权，不能由服务团队自行延长。
- 权限由服务端每次核验，撤销应影响已登录会话和后续工具请求；不能仅在页面隐藏入口。
- 区分只读辅导、起草建议和实际业务写入；敏感操作沿用原业务审批与MFA规则，不因获得远程访问而自动获得全部管理员权限。
- 记录申请、批准、使用、撤销和到期事件；日志避免保存密钥或完整客户聊天正文。
- 临时人工访问、Bot服务凭证、模型调用外发是不同授权，不能通过其中一项默许其余两项。

仍待确定：企业审批人、授权时长与上限、人员身份验证方式、网络连接方式、允许下载范围，以及撤销时正在运行的任务如何收尾。上述内容应在设计中写清并测试，不承诺不可实现的“撤销已下载文件”。

## 2.3 首期消息渠道确认补记（2026-10-31）

用户明确选择：**AI回复助手首期接入微信和邮箱**。

这与“Meta首选、Google其次”的投流优先级分别记录：前者是业务沟通消息渠道，后者是营销渠道，不互相替代。

待澄清微信是普通个人微信、企业微信客户联系还是微信客服；在确认具体类型、官方接口与权限前，不承诺自动读取全部聊天或自动发送。邮箱服务商、账号类型、历史邮件范围及接收／草稿／发送权限待明确。DSH的记忆不能替代渠道接入和原始消息存储。

## 2.4 微信测试载体确认补记（2026-10-31）

用户明确：**个人微信作为测试环境载体**。不再把是否使用个人微信作为待选问题。

仍需澄清测试交互方式：专门的Bot测试微信号接收业务员主动发送／转发的消息，还是读取业务员授权的选定客户会话；这两种方式对消息连接器、会话范围和发送确认的要求不同。尚未批准安装微信连接器、导入全部聊天、控制真实客户会话或自动外发。

助手建议先用专门测试账号与虚构资料验证消息、企业知识检索、上下文和回复草稿；具体个人微信连接方案、账户行为及故障处理需要技术验证，不能将运行DSH本身视为微信收发已接通。邮箱仍为另一首期消息渠道，服务商和授权方式待确定。

## 2.5 夜间自动接待与人工交接需求（2026-10-31）

用户进一步明确目标：客户在后半夜发送消息时，Bot读取指定客户会话，按问题查询企业知识库并自动回复；工作时间由业务员接手。因此，人工确认每次发送不再是全部时段的产品目标。原先草稿确认方式仍可用于工作时间及需要人工处理的问题。

助手推荐模式（细则待审）：持续监听企业授权的指定客户会话，以企业配置的时区、营业时间和工作日历切换“人工主导／Bot接待／等待人工”状态；人工可随时提前接管，发送前重新校验接管状态与权限，避免双方重复回复。自动监听不等于将整个微信账号全部会话纳入范围。

建议首期开通的自动回复范围：有审核资料支持的基础产品信息、FAQ、资料指引和需求收集。报价、折扣、确定交期、付款指示、合同变更和投诉处理的范围尚未确认；没有可靠资料时应收集问题、转人工，不捏造承诺。企业需确认Bot身份表达、允许调用的知识、客户数据外发及调用预算。

建议交接内容：夜间新增需求、原始消息引用、已发送回复、待确认事项和建议下一步。Bot访问凭证与企业员工、讲师临时访问分别授权；临时远程辅导授权不应成为夜间服务的隐含长期凭证。

个人微信采集端需要保持可用；当前没有验证其持续读取、自动发送、掉线检测及恢复可靠性。测试阶段只使用测试账号／虚构会话，不能据此声称已获得对真实客户的自动外发操作授权。开发验证需覆盖会话串线、去重、接管竞争、权限撤销、过时资料、断线和预算耗尽。

## 2.6 夜间自动回复业务白名单确认（2026-10-31）

用户明确允许：**产品资料、常见问题、需求收集，以及企业已经准备好的产品资料与报价单**；其他内容不开放给Bot自动处理。

已确认的功能边界：非工作时间，Bot可在企业指定客户会话中依据这些资料自动回复；工作时间由业务员接管。产品级自动接待需求不等于当前已获准在任何真实微信账号上发送消息。

| 类别 | 自动处理范围 |
|---|---|
| 产品资料 | 从企业批准对外使用的资料中检索和回答 |
| 常见问题 | 使用审核过的FAQ及适用规则 |
| 需求收集 | 询问并整理客户需求，保留客户原话与待确认项 |
| 现成报价单 | 只使用企业已有且批准对外的报价资料；不是授权模型自行定价 |
| 其他 | 转交人工；不能擅自承诺交期、变更付款要求、合同或其他业务条件 |

为落实上述边界，助手建议（具体字段和验收待设计）：报价资料需标明版本、有效期、币种、适用产品与规格、数量条件、贸易条件，以及适用客户／市场和可见人员。匹配条件不完整、过期、资料冲突或客户提出议价／超出原报价范围时，转人工；不根据记忆或算术推测新报价，不将采购成本表作为客户报价。

报价形式已由用户确认统一报价单，详见2.7。文件格式、数量与贸易适用条件、附件自动发送方式、对外Bot身份表达和允许模板仍待确认。

## 2.7 统一报价单确认（2026-10-31）

用户明确：使用**统一报价单**，不是按客户分别维护报价。结合已确认的企业独立部署与资料隔离要求，按每家企业自己的统一报价单设计；不跨企业共享私有报价。

用户已经允许Bot使用现成报价单自动回复，但没有授权模型自行定价、打折、调整交易条件或创建已确认业务单据。

为落实这一要求，助手建议的规则：企业审核并发布报价版本，Bot只使用适用且有效的版本；匹配产品／规格／计价单位／币种／数量条件及原有贸易条件。资料缺项、版本冲突、过期、表外报价、客户议价或额外费用未明确时，记录问题并转人工。报价单原件、结构化价格和回复引用应关联同一版本，便于人工接管与追溯。

统一价目表不代表无起订量、无规格差异、不含税运费或永久有效；这些条件需要读取原表并由企业审核，不能由模型推断。报价文件格式已确认为PDF（见2.8）；提取与人工审核方式、适用条件、审核人与生效方式仍待设计／样表核对。

## 2.8 报价文件格式确认（2026-10-31）

用户确认：统一报价单为 **PDF**。当前尚未提供样件，不能判断是否文本型、扫描型、带复杂表格或需要OCR，也不能声称已完成解析验证。

候选处理方式：

1. **PDF提取候选价格＋人工核对后发布（助手推荐）**：保留PDF原件和版本，先抽取产品、规格、金额、币种、单位、数量及报价适用条件；扫描件在技术验证后引入OCR；人工逐项核对报价条目和对外条件，通过后发布。Bot使用发布的确定性价格字段，并能回查对应PDF页码／原文，不自行补全缺失价格。
2. **人工维护价格条目＋PDF作为来源附件**：人工录入或导入价格结构，关联PDF版本后发布；解析依赖少，但资料维护工作量更多。

两种方式均需控制有效期、发布权限、价格精度与单位、原件版本对应、冲突／缺项、未命中和过期时转人工。提取置信度或模型自称正确不能代替企业审核。精确价格匹配应使用结构化条目，不仅依赖语义检索相似度。

用户随后回复“ok”，已选择方式1：PDF自动提取、人工审核后发布。自动发送PDF附件的能力、客户沟通模板及个人微信采集／发送技术仍需试验和明确授权。

当时核对到：DS Bot是DSH社区插件，存在长期会话、记忆和MCP能力扩展；源码有 `/api/bot` 内部通道。内部通道不是已承诺兼容的RESELAT接入API，需要适配器和版本契约。Bot／群组／团队记忆有不同共享范围，不能用Bot名称或提示词冒充租户隔离。

候选接法：工作台 → 已认证的任务接口 → 持久化任务／适配器 → DSH运行环境 → 受控业务工具 → 草稿与引用返回工作台。知识库、原始聊天与Bot摘要分别保存。数据库、财务授权、模型密钥与企业选择由确定性后台管理，不交给模型决定。

历史建议的最小工具：查询企业知识、读取有权访问的客户聊天与订单状态、保存回复草稿。真实发信、广告预算或订单写操作另设权限与审批。真实聊天需要渠道官方接入或明确授权的导入，安装Bot不会自动获得WhatsApp、Messenger或邮箱历史。

## 6. 投流与培训的候选范围

### 投流

- 企业推广方案、市场／客户群、产品卖点、素材、落地页、预算、负责人、方案版本与实验记录。
- Meta优先：账户与权限连接、广告花费及表现、线索进入客户、分派与跟进、有效询盘、报价及成交关联。
- Google后续复用渠道契约；回传方案按届时官方接口核对。
- 广告平台报告和系统内实际询盘／订单／回款分开记录统计口径、日期、币种与来源。
- “同一平台内独立投流工作区”是此前推荐，用户未明确选定；独立程序方案仍保留。

### 培训与辅导

- 共用经过讲师审核的外贸术语、流程步骤和课程知识；各企业私有资料独立授权。
- 真实业务与演练数据分开，训练不产生真实客户消息、订单或广告操作。
- AI解释当前步骤、检查准备资料、起草回复及整理跟进；讲师查看获授权企业的执行与辅导事项。
- 培训看板、课程／测验形式、员工学习数据可见范围尚未确定。

## 7. 历史部署路线比较（已选企业私有部署，见2.1）

| 路线 | 优势 | 代价／待证事项 |
|---|---|---|
| 每企独立实例，集中管理授权接入 | 复用当前单公司结构，数据与Bot运行环境容易明确隔开 | 多实例升级、备份、调度和跨企业运营管理成本 |
| 共用平台的多租户实例 | 统一开通、工作台、培训与更新，适合统一带运营 | 必须先改身份／成员和服务权限，再证明检索、文件、缓存、任务和Bot记忆隔离 |
| 先单企业Bot试点，再扩大 | 尽快验证知识命中、回复质量与实际费用 | 不能把试点绕过的租户问题留到30企业上线后再处理 |

OVH单机全栈试点、后续拆分Bot是此前建议，不是采购决定。机房、实际大陆网络、磁盘与备份、并发Bot资源、模型费用、维护负责人和恢复目标都需确认／测试。单机多容器不等于不同故障域；应用和Bot可先同机试点，但备份需独立保管并演练恢复。

## 8. 建议开发顺序（待确认）

这是启动讨论顺序，不是已批准的工程排期，也不预设购买服务器：

1. **P0：落实企业私有部署及授权边界**。企业服务器独立部署已确认；继续确定首批企业数量、你的团队与企业员工权限、集中辅导入口、演练和真实环境边界。
2. **P1：企业知识与客户会话基础**。资料审核／版本／授权，聊天来源、客户关联、检索权限和可追溯原文。
3. **P2：DSH技术试点**。锁定版本，通过受控工具读取数据，生成带依据的回复草稿，验证重启／取消／异常／隔离／预算。
4. **P3：Meta推广与询盘关联**。先证明数据同步和客户归因，再评估质量回传及受控写操作；Google后续。
5. **P4：培训与规模交付**。将经验证的流程形成可演练课程，逐批扩大企业，完成部署、备份恢复、监控与升级。

培训需求从P0就进入设计，P4仅表示规模化交付与验收，不是最后才考虑易用性。财务外部适配、完整生产／库存／质量追溯属于已有候选，用户未把它们指定为本轮优先项。

## 9. 开发启动前的最小待定项

1. 首批上线规模：2–3家试点还是30家一起进入；实际员工与Bot并发数量。
2. 企业私有部署和临时授权已确认；继续确定集中辅导入口、临时授权细则及允许汇总的数据。
3. 首期消息来源已确认微信＋邮箱，个人微信作为测试载体；继续明确Bot消息交互方式、邮箱服务商、历史导入范围及读写授权。
4. DSH的准确项目与版本；自主运行范围、资料外发、人工确认与每企／全平台费用上限。
5. 服务器是否已购买、实际机房和可用部署方式；目前会话中没有服务器账号／已购资源证据。

后续应先形成独立子项目的设计与验收标准，再写具体实施计划。本文没有安装依赖、启动Agent、购买服务、修改数据库、读取密钥、部署或自动发送客户消息。
