# 思链台双版本方案交叉评审与合并建议

评审输入：用户提供的“双版本、五个ports、自建Auth、MinIO、Ollama与Docker一体化”方案，以及此前《思链台本地化与二期扩展方案》。依据当前代码和官方资料逐项核对。当前代码基线为2a944a9，GitHub已实际通过224项测试和两种构建；这不是本地服务器端到端验收。工作区其他未提交的审计资料不属于本次评审变更。

## 1. 总体判断

采纳“一套业务逻辑、云端演示与客户私有化两种交付”的方向。首个付费版本以每客户独立实例交付，内外网访问同一个客户实例，身份/业务/文件独立于演示站。通过基础设施适配保持同一套订单、权限、金额、单据和审计规则。

需要调整的重点：不自行重写商业版认证底层；不默认新增MinIO；Mac的AI运行路径单独设计；补全财务、HTTPS、迁移与恢复；先验证交付门槛，再估工期。

线上演示能证明已展示功能，不等于客户本地安装、断网可用、备份恢复或安全边界已经验收。演示资料应明确标示虚构，不能混入付费客户真实资料。

## 2. 逐项取舍

| 用户方案 | 判断 | 合并建议与依据 |
|---|---|---|
| 线上演示、本地付费交付 | 采纳 | 共用代码版本，数据、账号、密钥和备份完全独立，不自动同步 |
| 基础设施ports解耦 | 采纳并收窄 | 围绕真实差异抽接口，避免为了目录结构重写所有SQL |
| 数据库几乎只改环境变量 | 部分成立 | postgres.js可复用；用途标记、TLS、角色、初始化、版本迁移和Auth表依赖仍要解决 |
| 推荐自己写Session/JWT/TOTP | 不作为首版路线 | 现有代码主要消费Supabase认证能力，不是已有完整的自建认证服务 |
| Better Auth因多一个依赖而次选 | 重新评估 | 要比较维护总成本；成熟认证库可能比自写密码/MFA/恢复成本更低 |
| 本地默认MinIO | 暂不采纳 | 首版已具备私有磁盘适配；MinIO社区仓库已归档，不宜沿用旧选型结论 |
| 邮件本地必配 | 调整 | 恢复账号的流程必备；SMTP是可选实现，严格离线场景还需人工恢复路径 |
| 本地强制Docker Ollama | 调整 | AI默认可关闭，不作为业务启动依赖；Mac优先评估原生Ollama连接应用容器 |
| 一体化Compose示意即交付方案 | 不成立 | 身份服务、TLS、初始化/升级/恢复、镜像与模型离线包还未包含完整 |
| SQL已冻结所以psql顺序执行即可 | 不成立 | 已应用脚本保持冻结，但新装/升级要有版本账本和checksum，不能重跑全量初始化 |
| 备份pgdata+miniodata | 不完整 | 数据库一致性备份、双库/文件一致窗口、必要密钥与实际恢复演练都要补 |
| 195项测试与3—4天交付 | 更新基线并取消承诺 | 当前224项；CI没有覆盖客户真实硬件、浏览器双模式、重启、断网与异机恢复 |
| 财务接口未单列 | 必须补齐 | 这是用户明确的交付需求，应与Auth/Storage/AI并列为集成边界 |

## 3. “数据不出内网”需要拆成可验收承诺

应提供两种客户网络配置，而不是同时承诺相互冲突的行为：

1. **局域网配置**：员工只在办公室/VPN许可范围使用；业务核心不依赖外部Auth、云存储和云AI。默认关闭业务数据外发；企业邮箱若在外网，发送邮件本身就是经授权的数据外发。
2. **远程访问配置**：数据仍存客户服务器，授权员工可从互联网HTTPS入口访问和下载；这会把资料传到员工设备，产品承诺应写“数据本地存储、受控远程访问”，不能写成“任何数据都不离开内网”。

“完全隔离网络安装”另外验收：安装镜像、npm产物、模型、字体、许可证及升级包都要事先交付；不能在install.sh现场执行联网拉取后称完全离线部署。VPN/隧道也需明确其联网依赖。双模式不等于演示站与客户站数据双向同步。

## 4. 接口如何抽：采用端口原则，不做空壳大重构

建议分工如下，名称与目录不必一次全部搬迁：

| 边界 | 应负责 | 不应负责 |
|---|---|---|
| DatabaseProvider | 获取用途专属postgres.js连接和事务、用途标记/TLS | 通用SQL语言、业务审批规则 |
| IdentityProvider | 密码登录、已验证会话、MFA绑定/挑战/验证、退出/吊销、账号开通及恢复 | 由前端角色声明直接授权业务 |
| StorageProvider | 私有对象create-only写、读、对象不存在/未知结果分类 | 决定订单能否下载、盖章审批 |
| MailProvider | 经授权事件的邮件投递及回执；默认disabled | 修改订单、绕过账号恢复验证 |
| FinanceAdapter | 版本化事件、幂等发送、回执和对账 | 会计入账决策、改变本系统原金额 |
| AiAdapter | 受限任务、经权限投影的上下文、结构化结果及来源 | 任意SQL/工具、自动批准业务 |

TLS证书属于部署网关与密钥生命周期，不需要塞进业务ports。原方案开头的五类插槽与后文mail列表并不完全相同；合并后采用上述六个真实边界，网关单独管理。

现有BusinessTx就是postgres.js事务类型，业务大量使用参数化模板SQL；线上和本地都是Postgres，没有理由换一个pg驱动或发明通用查询API。Storage已经有接口和磁盘实现，财务/AI已有契约，应逐步整理到单向依赖的端口模块，避免重复造接口。先迁一个真实业务路径并证明云适配无回归，再扩大迁移。

服务端与浏览器身份边界都要处理：当前MFA页面直接调用browserAuth().auth.mfa，代理刷新Cookie、管理员开户、active_auth_sessions视图也依赖Supabase。只改requireEmployee或新增四个API不能完整替换认证。

## 5. 身份方案：修正双方过于绝对的推荐

用户方案认为已有MFA/会话，换四个接口即可。代码事实：`src/modules/account/mfa.tsx`调用Supabase的enroll/listFactors/challengeAndVerify；`src/server/auth/session.ts`消费服务端验证的user/claims/aal/session_id，并查询私有成员状态与Auth会话视图。这是应用授权与外部认证集成，不是自行实现密码、TOTP密钥保护和完整会话生命周期。

自己实现还需覆盖：密码哈希参数/升级、登录限速、防枚举、服务端会话吊销/轮换、MFA挑战与防重放、密钥加密及备份恢复、丢失验证器的恢复流程、重置凭据后的旧会话失效、Cookie/CSRF、首管理员引导、审计。Session表与JWT可组合，但JWT不能让停用和吊销检查失效；不能由客户端或角色字段直接伪造“已通过MFA”。

合并建议：

- 云端演示继续现有Supabase，不更换认证。
- 本地短期基线保留自建Supabase Auth，便于复用现有行为和测试。
- **新增Better Auth对比实验，而非直接排除它。** 官方提供TOTP、备份码、可信设备及会话管理；仍需验证当前需求和部署成本。[2][3]
- 自写Auth不列为首个付费版本默认方案。是否长期采用自建Supabase，需要与Better Auth在容器资源、安装复杂度、撤权行为、恢复、迁移及维护成本上对比；不能只因“复用最多”就断言长期最优。

实验验收：相同的首次登录/管理员MFA、成员停用、退出后重放、管理员会话撤销、验证器丢失恢复和账号创建失败恢复，分别在本地运行；输出依赖清单、数据迁移差异与性能/维护记录。实验前不安装新运行依赖，不改现有云身份库。

## 6. 数据库：驱动能复用，初始化不能省略

双独立Postgres实例与同集群双database都可作为候选；后者共享Postgres角色命名空间与故障域，不能写成与两个独立实例同等隔离。当前代码用途URL路径固定为/postgres，选择同集群双database时还需明确允许的数据库名称、用途角色及标记验证。

`add-auth-session-view.sql`直接引用auth.sessions。裸Postgres没有自动创建这些Auth表，所以不能把所有身份SQL直接执行到空PG就认为身份服务完成。新装需要先准备身份提供者自有结构，再应用本系统迁移；更换提供者需要新的适配迁移，不能篡改已应用SQL。

新装/升级分别提供：目标检查、只应用未执行版本、checksum一致校验、失败状态和恢复方法、用途角色登录口令、两库相同公司UUID及员工映射、首管理员引导。迁移账号与运行账号分开；客户运行容器不持有数据库超级用户口令。

## 7. 存储：首版使用现有私有磁盘，保留S3扩展

当前API权限、文件大小/类型、来源引用、摘要和历史保留已形成边界，磁盘适配也已有create-only发布和路径防护。首个单机实例没有必须引入额外对象存储服务的证据。

截至本次核验，MinIO官方社区仓库标注2026-04-25已归档、只读，项目列出AGPLv3许可证。因此不能照抄“minio/minio无固定tag，一行启动”的旧建议。是否使用其他发行版或商业产品需另外评估维护、镜像来源及许可，不从归档状态推导所有相关产品均不能使用。[1]

S3兼容接口是保留方向，不等于选定MinIO。将来文件规模、多个应用副本或客户对象存储标准证明需要时再增加适配。

“文件预签名URL”与“财务印章图片/签名素材”是不同功能。现有下载经过订单/CO授权与归档状态检查，首版继续API流式授权下载。增加预签名URL时，需要另外定义短时有效期和撤权/作废后的行为；不能用存储驱动替代签章审批。

## 8. AI：Mac/Linux分开，业务不依赖模型在线

Ollama官方FAQ明确：普通Ollama Docker容器在macOS Docker Desktop上不提供GPU加速。因此Mac Studio原生已跑通，不能证明同模型放进Compose仍有相同性能。[4]

候选运行配置：

- Mac：应用/数据库容器化；Ollama优先宿主机原生运行，应用服务端通过受控宿主机地址访问，实际验证容器到宿主网络与防火墙。
- Linux NVIDIA：单独GPU配置文件，验证驱动和container toolkit后启用；不使用示例中的`deploy.resources: gpu: null`占位当作有效GPU配置。
- 无AI客户：AI功能关闭，模型不可用不阻止订单、PDF和收付款。AI不应出现在app启动的强制depends_on里。

Ollama也有云功能；“用了Ollama”本身不能证明没有外发。本地模式配置官方`OLLAMA_NO_CLOUD=1`、允许的本地模型/服务地址、出站策略并验证；不在模型不可用时静默回退云API。[4] 模型按硬件、任务准确率、上下文与并发实测选择，不在本方案固定Qwen2.5的7B/14B/32B作为所有客户标准。

初期优先询盘提取、翻译和跟进摘要；PI/CI/PL的金额、数量、税号、主体和版本继续由确定性业务规则生成，AI只能辅助可复核文本。客服知识库是外部访问与数据发布的新边界，暂不与内部订单助手捆绑首发。

## 9. 邮件与财务补齐

账号恢复必须有操作流程；SMTP不是严格离线客户的普遍前提。局域网可接客户内网邮件服务或受控管理员恢复，互联网SMTP/邮件API需明确允许的数据范围。订单确认/询盘提醒属于另行设计的通知需求，不因加mail接口就视为已授权发送。凭据不进前端，投递失败不回滚已提交订单。

财务必须有独立端口。沿用已有schemaVersion=1事件：确认/冲销、companyId、eventId、业务日、currency、amountMinor整数字符串、原事件引用。后续业务事务写outbox，独立worker使用财务专属凭证；超时先查对账状态，区分“已接收”和“已记账”，不重复生成凭证。财务停机不阻塞本地业务；只做接口预留时不启动外发。

## 10. Docker和交付脚本需要补什么

用户的Compose适合作为概念示意，不是当前可运行部署清单：缺少选定的Auth服务、双库用途初始化、网关/TLS、完整健康检查、版本固定以及升级/恢复流程。`depends_on`还需服务健康/就绪条件；不把AI或SMTP当核心业务启动前提。

应交付两种组合：基础包（app、身份服务、双库、私有文件、HTTPS网关）+ 可选包（AI、邮件、财务worker）。Mac AI为宿主机可选服务仍属于统一交付，不必强求所有进程在同一个Compose文件。

| 工具 | 必须做到 |
|---|---|
| install | 预检、密钥生成/导入、目标与用途校验、初始化、首管理员、TLS信任；已有安装拒绝重建 |
| upgrade | 指定版本及镜像digest、备份、只执行新增迁移、兼容性/失败检查与旧应用回退 |
| backup | 两库逻辑备份或经验证物理备份、文件与元数据一致窗口、必要密钥、版本清单、加密与校验 |
| restore | 在全新环境恢复身份/业务/文件、文件摘要及账号权限验证；明确恢复点 |
| healthcheck | 区分存活与DB/Auth/对象就绪；诊断不泄露密钥；AI离线只标功能降级 |

不能直接打包运行中的pgdata当可靠备份。PostgreSQL文档明确，普通文件复制需要停库；在线物理备份要依赖一致性快照/正规备份机制及WAL。逻辑备份双库也需协调业务文件和跨库写入的一致性窗口。[5]

## 11. 合并后的开发顺序

| 阶段 | 交付物 | 验收点 |
|---|---|---|
| M0 架构证据 | 已有224测试CI、唯一workspace、真实文档、演示基线；本评审 | 证据与已实现/候选清楚分开 |
| M1 身份选型实验与最小端口 | Supabase自建/Better Auth对比，身份/存储/财务/AI等端口整理 | 云行为不变；本地MFA、停用、吊销、恢复可验证 |
| M2 全新机器可安装 | 基础部署包、用途角色/迁移工具、首管理员和HTTPS | 完全从零安装，不靠开发者临时改库 |
| M3 双网络与灾备 | 局域网及远程访问配置、断公网、升级/回退、备份恢复 | 内外同实例一致；异机恢复后可登录并下载校验文件 |
| M4 首个财务适配 | 客户沙箱或约定导入格式、outbox、幂等与对账 | 重放/超时/冲销不重复入账 |
| M5 AI可选试点 | 一种硬件、一个模型、一个任务 | 有权限和来源，模型离线业务正常，确认后才写业务 |

API连通原型与收费交付分别估算。当前没有客户服务器、身份实验和财务接口规格，6.5天或多Agent3—4天均不能作为交付承诺。并行适合已确定契约的独立模块；身份、迁移、网络与恢复有依赖，不能简单按Agent数量折半工期。

## 12. 对我上一版方案的修正

- 保留：模块化单体、每客户实例、内外同数据、确定性业务规则、财务outbox、AI权限投影、按安装/恢复门槛交付。
- 加强：采纳用户的端口组织与线上适配先迁移思路，补邮件能力边界；区分演示与客户独立发行配置。
- 修正：自建Supabase只作为低改动基线，不预设长期最优；增加Better Auth实证比较。
- 增补：MinIO当前归档事实、Mac AI分离运行、Ollama禁云模式、严格离线与远程访问的承诺区别，以及活跃PG目录不能随意复制的恢复要求。

本轮只完成交叉评审和文档归档，不切换认证、不安装依赖、不改云库/线上部署、不启动AI或财务调用。推荐下一步进入M1实验，以结果确定身份提供者后再扩大本地安装开发。
