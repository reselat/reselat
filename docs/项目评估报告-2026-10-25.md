## 三、代码简洁度评估：9/10

这是本项目做得最出色的部分。以下几个设计值得单独说明：

### 1. 金额使用 BigInt，而非浮点

外贸系统的命门是钱。`src/domain/money.ts`：

```ts
export function lineAmountMinor(quantity: string, unitPrice: string, currencyScale: number): bigint {
  validateScale(currencyScale);
  const q = decimalParts(quantity), p = decimalParts(unitPrice);
  const product = q.units * p.units;
  const shift = q.scale + p.scale - currencyScale;
  if (shift <= 0) return product * 10n ** BigInt(-shift);
  const divisor = 10n ** BigInt(shift);
  return (product + divisor / 2n) / divisor;   // 半进位处理
}
```

配合 `src/domain/decimal.ts` 拒绝 `1e3`、`NaN`、`1.2.3` 等非法输入。

测试直接以 **`9007199254740993.01`**（超过 `Number.MAX_SAFE_INTEGER`）验证 ——
这种测试用例说明写代码的人清楚自己在防什么。

### 2. 连接数据库前先验明正身

`src/server/db/client.ts` 建立连接后立即执行：

```ts
const rows = await sql`select purpose, project_ref
  from trade_private.deployment_identity`;
verifyTargetMarker(rows.map(r => ({purpose: r.purpose, project_ref: r.project_ref})),
  purpose, target.projectRef);
```

**连错库直接拒绝服务。** 双库架构下串库是灾难性事故，
这个防护成本极低，但绝大多数人想不到加。

### 3. 错误处理达到生产级成熟度

`src/server/business/http.ts` 中最关键的一段：

```ts
if (['CONNECTION_CLOSED','CONNECTION_ENDED','CONNECT_TIMEOUT',
     'ETIMEDOUT','ECONNRESET','08000','08003','08006','57P01'].includes(code))
  return Response.json({ok:false, code:'RESULT_UNKNOWN',
    message:'提交结果尚未确认，请保留原请求重试核对。'}, {status:503});
```

`RESULT_UNKNOWN` —— 这句体现的核心认知是：
**网络断开时，业务到底成功与否是未知的**，绝不能告诉用户"失败"。

同时完整覆盖了 Postgres 原生错误码：`42P01` → 「数据库迁移未应用」，
`23514/23505/23503` → 「业务约束冲突」。

### 4. 权限模型克制，不过度设计

仅 3 个角色，一个 `assertScope` 函数完成核心判定（`src/server/business/access.ts`）：

```ts
if (actor.role === 'operations' && resource.operationsId === actor.id
    && (action === 'read' || action === 'fulfill')) return;
if (actor.role === 'sales' && resource.ownerId === actor.id
    && (action === 'read' || action === 'write')) return;
```

配套 `projectFields` 将 `costPrice`、`supplierId`、`bankAccount`
从业务员可见字段中剥离。

**业务员看不到采购价与公司银行账号** —— 这是外贸公司真实的核心诉求，做对了。

### 5. 测试不做假

`tests/business/command-identity-integration.test.ts` 使用
PGlite（内存中运行真实 Postgres）+ mock 掉 `@/server/db/client`，真实验证：

- 员工 version 过期 → 写操作被拒
- 员工被停用 → 写操作被拒
- 更换 actor 复用同一 `requestId` → `IDEMPOTENCY_CONFLICT`
- 事务回滚后，单号稳定重放为 `SO-20261024-00001`

**比 mock 掉整个数据库的测试强一个量级。**

## 四、二次开发迭代友好度：5/10

以下是三个具体的技术债，按严重度排序。

### 债 1（最严重）：`demo` 与 `workspace` 是两套并存 UI

```
src/app/demo/       → catalog, customers, finance, orders,
                      refunds, settings, suppliers, orders/new, orders/[id]
src/app/workspace/  → audit, catalog, customers, documents, orders,
                      payments, purchases, refunds, settings, shipments,
                      signatures, suppliers, orders/new, orders/[id]
```

modules 层同样分裂为三套：`modules/demo/`、`modules/workspace/`、`modules/business/`。

这是历史演进产物：先用 localStorage 单机版验证业务逻辑
（`src/modules/workspace/store.ts`），再做 Supabase 共享版。

**后果：修改一个客户字段，可能需要改两处。此债随时间线性增长。**

### 债 2：单个巨型路由（需辩证看待）

`src/app/api/workspace/business/route.ts`（76 行）承载了
**约 20 个 GET view + 约 30 个 POST action**，全部通过 `switch` 分发。

**对迭代有利的一面：**
- 新增操作只需加一个 `case`，无需新建文件、无需配置中间件
- 错误处理天然统一
- 命令式 + `requestId` 幂等，非常适合外贸单据这类事务性操作

**对治理不利的一面：**
- 缺乏 HTTP 语义 → 无法使用 CDN / 路由级缓存
- 无法针对单个操作附加细粒度中间件
- `maxDuration=300` 意味着 Vercel 上是一个长期存活的大函数，
  冷启动与可观测性都受影响

**结论：短期看这个设计是对的，长期需要拆分，但不紧急。**

### 债 3：Git 资产几乎为空

10 个 commit 全部形如：

```
ae36743 巡检 2026-10-25 09:21 · 代码变更 24 文件
a8e869c 巡检 2026-10-25 09:06 · 代码变更 25 文件
```

由自动巡检机器人提交，**零语义信息**。

且 README 自述：「没有 Git 初始化／提交／push；本地文件不是异地备份。」

**这条独立于代码质量，属于资产安全问题，需严肃对待：**
2334 行源码 + 2190 行文档 + 61 个测试文件，
目前仅存在于本机外置盘。盘损即全损。

## 六、行动建议（按性价比排序）

### 建议 1：立即处理 Git 与文档事实源 ⏱ ~20 分钟

两件事各约 10 分钟，消除的是最大的风险与最大的困惑：

1. **添加 Git remote 并推送**。这是唯一有时间压力的事项。
2. **将 6 份过期方案文档移入 `docs/archive/` 或删除**，
   README 只保留单一事实源。

### 建议 2：明确 `demo` 的去留，建议「冻结」而非「维护」

建议：不再新增功能，并在其目录挂 README 标记说明已冻结。

理由：`demo` 已完成「验证业务逻辑」的历史使命，
当前它的持续存在纯粹在稀释注意力。

### 建议 3：暂缓新增业务模块

当前阶段新增功能的边际收益，
低于**先将 `workspace` 收敛为唯一真源**。

否则每加一个功能，都在同时加重两套代码。

### 附带提醒

README 提及的依赖链高危公告：
`eslint-config-next → fast-glob → micromatch → braces`

属 devDependency 链，**不影响运行时**。
但正式上生产前需跟进处理（不要使用 `audit fix --force` 降级框架掩盖风险）。
