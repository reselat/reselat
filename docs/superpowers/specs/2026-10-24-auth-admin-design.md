# 多用户登录、管理员后台与共享数据库接入设计

日期：2026-10-24。状态：用户已批准本地实现、列明依赖和零预算独立测试项目创建；具体云端迁移仍需本地验证后确认。

用户修订：只设admin/sales/operations，不设置finance角色。财务功能保留业务台账，后续预留API对接现有财务系统，以下原设计中的finance列与角色提议撤回，不实施。

## 1. 目标与现状

用户要求多员工登录、管理员页面、数据库业务资料维护与角色分配；用户已选择独立外贸测试项目。

当前应用是单浏览器localStorage试用：/demo包含客户、产品、订单、收付款、合同与单据、HS和退税清单。已有authorize纯规则与字段投影测试，但真实身份与数据库尚未接入。仅增加登录页面不能实现多员工协作；必须同时替换浏览器业务状态读写。

保持单公司主体，不建设SaaS租户管理或任意SQL控制台。

## 3. 登录与员工生命周期

- /login：邮箱密码登录，明确失败/停用提示；退出登录；重置密码流程在邮件配置后启用。
- 内部系统不公开自助注册。Supabase Auth账户不自动获得员工权限，必须有本公司启用的员工记录。
- 使用官方SSR Cookie会话方案。每个受保护服务端请求验证可信身份，再读取当前数据库员工状态和角色；不相信客户端role、companyId、ownerId或可编辑user_metadata。
- 停用、撤权后下一次业务请求即拒绝，不等待旧JWT角色失效。敏感管理员操作额外校验MFA和服务端会话有效性。
- 管理员首次使用必须配置TOTP MFA；未完成时只允许登录/绑定/退出，不能管理员工或业务数据。
- 首个管理员通过受控引导设置：只有明确指定的Auth用户ID、公司、一次性运行授权；不存在公开“注册即管理员”或通用后门。
- 邀请邮件、密码重置等外发默认关闭；接入邮件服务及向真实邮箱发送前展示收件人和内容并按规范确认。代码可先准备，不能以邮件接口调用成功冒充收件成功。

## 4. 固定角色与范围（需人类审核）

| 权限 | 管理员 admin | 业务员 sales | 运营 operations |
| --- | --- | --- | --- |
| 员工启停、角色、范围分配 | 是，MFA | 否 | 否 |
| 客户、销售订单 | 全公司 | 自己负责/明确共享 | 仅分配任务所需字段 |
| 产品与HS基础资料 | 维护 | 查看选取 | 授权维护 |
| 采购/供应商/采购价 | 是 | 默认隐藏成本 | 明确采购权限和任务范围 |
| 出运/装箱 | 是 | 本单查看/提交 | 分配订单操作 |
| 收付款/冲销/退税资料 | 是 | 本单已收/未收摘要 | 脱敏进度 |
| 公司/银行资料 | 维护并留痕 | 单据必需字段 | 单据必需字段 |
| 正式单据确认 | 是 | 提交 | 提交 |
| 批量导出/签名 | 单独能力授权 | 默认否 | 默认否 |

按用户修订只保留三个角色；收付款台账由明确授权人员维护，不新增财务角色，不建设自定义角色编辑器。后续以API对接现有财务系统。

销售员不能修改客户归属或将资源共享给自己。订单只能关联其有权访问的客户。运营不因拥有采购任务而取得全部客户/销售金额。管理员也必须匹配本公司。

## 5. 管理员后台

/admin使用同一应用与数据服务，所有页面和API均服务端鉴权。

- 员工管理：账号关联、启停、固定角色、客户/订单范围与专门能力分配、最近状态；不显示密码、令牌或高权限凭据。
- 防误操作：最后一名启用管理员不可停用/降级；并发变更在事务内串行校验；管理员不能通过请求正文伪造操作者。
- 业务资料管理：客户、产品、HS、供应商、公司资料；校验、分页、搜索、归属分配。利用现有页面，按权限提供操作。
- 系统状态：数据库连接、Schema版本、业务记录数量及可验证的备份状态。无真实备份证据时不显示“备份成功”。
- 操作记录：权限、账号、归属、银行变更的操作者ID、对象ID、时间、动作和版本。日志与审计避免存储敏感正文和密钥；不声称数据库超级管理员无法篡改。
- 不开放SQL执行、任意表浏览、删库、数据库超级管理员权限或云服务控制台代理。

## 6. 共享数据与授权架构

浏览器→受保护业务API→统一授权/字段投影→私有schema trade_private→Supabase PostgreSQL。

Auth登录是浏览器访问Supabase的明确例外；普通业务表不向浏览器Data API开放。业务API使用专用app_backend数据库角色，无DDL、超级用户或BYPASSRLS；高权限Auth管理密钥只存在隔离员工管理适配器。

- 基础实体：companies、employees、employee_capabilities、customers、customer_shares、products、suppliers。
- 业务实体：orders、order_lines、purchases、purchase_lines、shipments、shipment_lines、payments、documents、refund_checklist、followups、customs_changes。
- 范围与并发：业务实体有company_id，需分配对象有owner_id/分配关系，统一version。外键约束防止跨公司关联。
- 金额为整数最小单位；业务命令计算金额，不接受浏览器权威total、支付余额或审计字段。
- 单据采用不可变快照；已有合同和历史HS版本继续可重下，员工只能获取授权的快照。单据确认/作废另有命令，不能覆盖历史。
- 付款不超额、分批出运不超量、最后管理员保护、角色更新在数据库事务/锁与条件版本内校验。重复请求使用幂等键；版本冲突返回409，不全量后写覆盖。
- 不将整份Workspace JSON存进一行或整份返回所有员工；这会泄露成本且丢失并发更新。分页列表与按对象命令逐个替换现有useWorkspace.update路径。
- 角色变更只更新数据库权威记录，JWT/页面菜单不充当授权依据。
- 业务schema不暴露Data API，撤销anon/authenticated访问；确需暴露的表必须额外RLS并实测。不能为了绕过权限报错使用service_role做普通业务读写。
- Cookie与含身份响应no-store；不使用共享缓存缓存人员范围。写接口校验同源/CSRF；登录限速先使用Auth能力，业务敏感接口另有限速与审计。
- /demo继续只供虚构本地试用，不作为登录后后台入口。正式工作区与PDF接口完全走服务端受控路径；不能继续调用匿名loopback demo接口。清晰标注数据环境，不自动上传本地资料。

6. 首位管理员邮箱/真实员工账号在实际引导前单独确认；不要求在聊天粘贴密码或密钥。

## 8. 验收门槛

- 未登录的页面跳登录，API返回401；缺员工/停用/跨公司/超范围返回403，不能枚举资源正文。
- 两名业务员无法互读未共享客户/订单；撤销共享下一次请求拒绝。业务员DTO不含采购成本、利润、无关银行或员工敏感字段。
- 非管理员直接请求admin API、篡改role、伪造user_metadata不能提权；管理员MFA未完成不能改权限。
- 最后管理员的并发降级/停用不能导致零管理员。
- 运营可做明确授权动作且不能扩权；业务员未收款摘要不等于获得全部财务流水。
- 两个账号依次保存资料并重新登录后可读授权共享数据；不同并发更新冲突明确返回，不丢失旧记录。
- 真实Cookie刷新、退出、密码重置令牌、停止账号和会话失效分别验证；mock测试不等于Auth集成通过。
- PDF/合同/HS/收付款/退税现有功能在授权工作区回归；至少一个多人完整业务闭环。
- 既有78测试保留，全量测试/类型/lint/build与独立只读安全复核通过；云端SQL顾问无未处理关键权限问题。统计本地/测试环境层级，不宣称生产完成。
