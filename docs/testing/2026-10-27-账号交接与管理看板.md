# 账号设置、员工交接与管理看板

## 使用流程

所有角色在侧栏底部进入“个人账号设置”。姓名保存到身份库员工目录，联系电话为本人 Auth 联系资料，不作为已验证短信登录号码。不能修改自己的角色、公司或状态。密码通过 Supabase Auth 修改，填写当前密码与两次新密码；服务要求重新验证时可发送安全验证码。邮箱变更需完成服务配置要求的新旧邮箱确认，支持手动填写 email_change 验证码；未确认前保留当前登录邮箱。邮件投递依赖身份服务 SMTP/限额，不能把提交成功当作投递或邮箱变更完成。

所有已绑定验证器的角色登录后均需 MFA；管理员继续强制 MFA。换机先验证旧设备，再绑定、验证新设备，最后移除旧设备。前端禁止移除最后一个已验证设备；身份服务本身仍是账户安全权威。丢失所有设备不提供无验证自助绕过。MFA 验证页支持选择多个已验证设备。

管理员在成员管理停用离职员工，再进入“员工离职交接”。读取成员，可分页继续加载。选择已停用/归档来源和启用接手人，预览范围、填写说明、确认交接。客户/销售归属要求销售或管理员；运营分配要求运营或管理员；供应商要求管理员。若跨多种职责，可交给管理员后另行分配。

交接在同公司范围内执行，持有身份公司/成员锁并通过业务公司锁串行化；业务归属与共享权限在单个业务事务更新，失败回滚。预览指纹绑定来源、目标、记录/订单版本与共享清单；变化后须重新预览。使用持久请求编号实现重试幂等，保留未知结果核对入口。来源账号保持停用，不在交接时重新启用，也不删除员工。

已完成/取消订单一并移交，运营分配一并变更。采购、到货、出运、收付款、单据、退税与订单文件沿原订单关联可见，仍受接手角色字段与模块权限约束。保留历史创建人、操作人、冻结销售版本、金额、凭证和文件；签章授权不随员工移交，需另行审批。历史审计和原始文件不复制、不删除、不改写。

## 管理看板与口径

独立一级菜单“管理看板”，路径 `/workspace/management`；`/workspace` 重定向到此。业务台只保留销售、采购与单据。保留原业务余额、订单状态、逾期和到期跟进面板。

每日客户开发按北京时间日期查询：新增客户取首次创建的主档，并归属最早 `record.save(kind=customer)` 的操作人；编辑/重试不增加，客户交接不重新归属历史业绩。无对应创建审计的异常旧资料不猜测开发人。跟进次数按登记业务日期统计，同一成员当天同一客户只计一个跟进客户；全员“跟进客户人次”是各成员去重后的数值相加，不声称是公司去重客户数。

管理员看到所有角色，包括零数据与已停用成员；其他角色只看到本人。运营目前不开放新增客户权限，零数据正常。每日开发统计不改变现有客户/跟进写权限。

## 数据库与发布

唯一追加 SQL：`scripts/sql/employee-handover.sql`，仅向既有私有业务角色 `business_backend` 授予 `order_shares` DELETE，以便交接时撤销离职人的共享权限。不授予公网角色，不改变表结构/历史资料，不接触身份库 DDL、不创建资源或收费项。现有 `record_shares` 已具有 DELETE 权限。SQL 自身不交接任何员工资料。

发布失败可回退应用版本；新增权限不导致数据格式变化，可保留。若要撤回交接能力，先停用应用入口，再 revoke delete on trade_business.order_shares from business_backend。已执行交接应由管理员反向办理，不通过删审计恢复。未替用户选择员工或在云端执行真实交接、修改真实密码/邮箱/验证器。

验证证据见同日 evidence 文档。后续在测试站人工验收邮件投递、真实验证器换机与具体员工交接，避免把隔离模拟当作云端身份服务验收。
